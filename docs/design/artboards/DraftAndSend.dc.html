Why "Queued" gets its own state instead of being called Sent Measured on 2026-09-10: the send call returns success long before anything has left the building. Treating that success as "sent" is the single easiest way to build a client that lies — and the lie is the worst kind, because the agent moves on and the customer never hears back. So the interface waits for the platform to say Sent, and says Queued until then. If it is still queued after a short wait, it keeps saying queued. It never upgrades itself out of hope.
And a stuck message must surface. If a mail is still queued minutes later, the thread shows it as Queued — not sent yet with a way to check or resend, rather than sitting silently in a state the agent believes is finished.

What is checked, in order
1Does this organisation require sending mailboxes to be approved at all?
2Is this case's queue approved? (We send as the queue, not as the agent — which is what the standard form does.)
3Is its mailbox actually connected and last-tested successfully?
A fourth outcome: we could not tell. If the check itself fails, that is treated as not safe, not as fine. "Probably approved" is not good enough when the failure mode is a customer never getting an answer. Checked once per case and remembered, so it costs nothing per reply.
A counter-intuitive detail worth keeping: a queue with no address fails loudly and immediately. A queue with an unapproved address fails silently and forever. Do not infer one from the other — the loud case is not evidence the quiet one is covered.
